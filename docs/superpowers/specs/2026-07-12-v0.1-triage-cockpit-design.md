# pgops v0.1 — "The First Five Minutes" (triage cockpit) — design spec

**Date:** 2026-07-12 · **Status:** approved direction, full spec for review

## 1. Mission

> Type `pgops` during an incident. In 60 seconds you know whether the problem is
> locks, a runaway query, a stuck transaction, or connection exhaustion — and you
> can act on it and paste the evidence into the incident channel.

pgops' niche is unchanged: pgHero is the daily dashboard, pgBadger is the
postmortem, **pgops is what you run during the incident**. v0.1 makes that claim
true as a *single tool* rather than a set of subcommands the user must already
know how to choose between.

### Why this shape (product reasoning)

Dev-adopted single tools (k9s, lazygit, htop, fzf) share four properties:
one command with instant payoff; one *complete* job rather than many partial
ones; expertise encoded in the tool (what to look at first); and shareable
output. pgops' target user is a **dev on call, not a DBA** — they know "the
database feels wrong," not which of eight subcommands maps to their symptom.
`dba-playbook/00-first-five-minutes.sql` is the DBA's orientation pass written
down; v0.1 turns that file into the product's front door. The wide roadmap
(vacuum, slots, parts, review, explain, events) collapses from "8 sibling
products" into "future drill-downs behind one triage screen."

## 2. Current state (as of this spec)

**Built and tested (70 tests, 13 files):**
- `locks` — lock-chain tree (root blocker + waiter cascade), selection-driven
  disclosure, advise heuristic, kill with confirm modal + audit log +
  selection-pinned-to-pid + PID-reuse session-identity guard (`backend_start`
  re-check; uncommitted but complete in the working tree), `--snapshot` one-shot
  and `s` snapshot-to-file.
- `top` — live `pg_stat_statements` view (sort/filter); no `--snapshot` parity yet.
- Shared core: connection pool, snapshot writer, theme, audit log, filter,
  list-navigation hook, freshness/status bar.
- `dba-playbook/` — six annotated SQL files mirroring the roadmap.

**Gaps this spec addresses:** no entry point for "I don't know what's wrong";
idle-in-transaction (the #1 dev-caused incident) has no view and no action path;
kill logic is locks-specific; snapshot coverage is uneven.

**Gaps deliberately deferred to the ship milestone (M4):** npm publish (names
`pgops` and `pg-ops` both free as of 2026-07-12), CI, README rewrite, demo GIF,
community scaffolding.

## 3. Product definition

### 3.1 The cockpit (`pgops` with no subcommand)

A live, read-only triage screen; refresh on the same poll cadence as `locks`,
freshness shown in the status bar.

```
 pgops — postgres://…/appdb                                     ● live · 2s ago

 SESSIONS                               CONNECTIONS
 active               12                47 / 100 used · 53 headroom  ✓
 idle                  31
 idle in transaction    3  ⚠ oldest 14m

 BLOCKED   ⚠ 4 pids waiting · root pid 3990 · longest 2m 10s

 LONG-RUNNING
 pid 3990 · 41m · active · SELECT * FROM orders WHERE …
 pid 5122 ·  6m · active · REFRESH MATERIALIZED VIEW …

 HEALTH  wraparound 34% ✓ · repl slots: 1 inactive, 2.1 GB retained ⚠

 j/k panels · Enter drill in · s snapshot · q quit
```

**Panels** (all queries adapted from `dba-playbook/00`, `03`, `04`; all
read-only; all client-backend-scoped where applicable):

| Panel | Source | Verdict logic | Enter drills into |
|---|---|---|---|
| SESSIONS | `pg_stat_activity` grouped by state, plus oldest idle-in-txn age | ⚠ if any idle-in-txn older than 1 min; critical ≥ 5 min | `sessions` view |
| BLOCKED | count of pids with `pg_blocking_pids() ≠ ∅`, longest wait, root pid | ⚠ if any blocked; critical if longest wait ≥ 1 min | `locks` view |
| LONG-RUNNING | active client queries running > 5 s, top 3 by duration | ⚠ if any > 30 s; critical > 5 min | `sessions` view, pre-sorted active-by-duration |
| CONNECTIONS | used / `max_connections` / headroom | ⚠ headroom < 20 %; critical < 10 % | `sessions` view |
| HEALTH (cards) | wraparound: max `age(datfrozenxid)` as % of `autovacuum_freeze_max_age`; slots: inactive count + retained WAL from `pg_replication_slots` | ⚠ wraparound ≥ 75 %, critical ≥ 90 %; ⚠ any inactive slot retaining > 1 GB | *nothing* (see below) |

**Health-card discipline:** a card is one line — verdict symbol + the key
number. Never a panel, never interactive in v0.1. A warning names the object
and points at the remediation source (e.g. `inactive slot 'debezium' retaining
2.1 GB — see dba-playbook/04`). These cards are the honest placeholder for the
future `vacuum` and `slots` views.

**Keys:** `j`/`k` move panel focus · `Enter` drill into focused panel ·
`t` open `top` (aggregate slow-query stats have no panel of their own — live
long-runners are sessions; `t` keeps `top` one keystroke from the hub) ·
`s` snapshot to markdown file · `q` quit. In a drilled-in view, `Esc` returns
to the cockpit (only when the view was entered from the cockpit; direct
`pgops locks` behaves exactly as today — `Esc` does nothing, `q` quits).

**`pgops --snapshot`** prints the whole triage screen as markdown to stdout
and exits — the paste-into-Slack artifact. `pgops --help` still prints help.

### 3.2 The `sessions` view (new)

`pgops sessions`, or Enter from SESSIONS / LONG-RUNNING / CONNECTIONS panels.

- One row per client-backend session: pid, state (colored; idle-in-txn red),
  time in state, application_name, user, client address, query (truncated;
  full on selection, same disclosure pattern as locks).
- Default sort: idle-in-transaction first (oldest first), then active by
  duration, then idle. When entered from LONG-RUNNING: sorted active-by-duration.
- `/` filter (existing filter core), `j`/`k` navigate, `s` snapshot,
  `x` kill — **the same hardened path as locks**: confirm modal, audit-log
  entry, `backend_start` session-identity guard, outcome messages
  (`terminated` / `session changed — not killing` / `already gone`).
- `--snapshot` one-shot parity.

### 3.3 Kill generalization

`src/commands/locks/kill.ts` moves to `src/core/kill.ts`. Target type becomes
`{ pid: number; backendStart: string | null; description: string }` (description
feeds the audit log and messages). `locks` and `sessions` both call it. There is
exactly one code path in the product that can terminate a backend.

### 3.4 Snapshot parity

`--snapshot` one-shot and `s` in-view snapshot work on: cockpit, locks (done),
top, sessions. Each view owns a pure `render.ts` (markdown) as locks does today.

### 3.5 Graceful degradation (first-run experience on managed Postgres)

- Missing `pg_stat_statements` → `top` explains and prints the enable SQL
  (existing behavior; cockpit is unaffected — no cockpit panel depends on it).
- Insufficient privilege for `pg_replication_slots` / wraparound query →
  that card shows `n/a (needs pg_monitor)` with the grant SQL; other panels
  unaffected. A query failure in one panel never blanks the cockpit.
- No `pg_signal_backend` → kill fails with the grant SQL in the message
  (existing locks behavior, carried into sessions).

## 4. Architecture

Follows the established per-command pattern (SQL in `query.ts` → pure
transform → pure markdown `render.ts` → Ink component):

```
src/commands/home/      query.ts   — triage + health SQL (from playbook 00/03/04)
                        model.ts   — rows → panel models + verdicts (pure)
                        render.ts  — cockpit → markdown (pure)
                        Home.tsx   — panels, focus, drill dispatch
                        index.tsx  — poll loop, --snapshot one-shot
src/commands/sessions/  query.ts · model.ts · render.ts · Sessions.tsx · index.tsx
src/commands/top/       render.ts gains snapshot; index.tsx gains --snapshot
src/core/kill.ts        generalized kill (from locks)
src/cli.tsx             bare invocation → home; subcommands unchanged
src/ui/…                unchanged (navigation, filter, status bar reused)
```

**Hub navigation:** `cli.tsx` renders a root `<App initialView=…>` holding a
one-deep view stack: `home` ⇄ (`locks` | `top` | `sessions`). Drill = push,
`Esc` = pop. Views receive an optional `onBack`; when absent (direct subcommand
entry) they render exactly as today. Each view keeps its own poll loop; a view's
poll starts on mount and is cancelled on unmount (fixing the known in-flight
poll leak noted in the 2026-06-26 review follow-ups as part of this work).

## 5. Error handling

- Connection failure at startup: same behavior as current commands (clear
  message + exit code 1).
- Per-panel query failure on the cockpit: panel renders its error inline;
  the rest of the screen stays live (Promise.allSettled over panel queries).
- Kill-path errors: unchanged from locks (message with cause; audit entry
  records the failure).

## 6. Testing

Same strategy as the existing 70 tests:
- Pure layers (`model.ts` verdict logic, `render.ts` markdown) — unit tests,
  including threshold edges (headroom 19 %/20 %, idle-in-txn 59 s/61 s,
  wraparound 74 %/76 %).
- `Home.tsx` / `Sessions.tsx` — `ink-testing-library`: panel focus movement,
  drill dispatch, Esc-pop only when entered from home, kill confirm flow in
  sessions (reusing locks' test patterns), disclosure invariant.
- `core/kill.ts` — existing `kill.test.ts` moves and stays green; both callers
  covered.
- `--snapshot` one-shot for home/sessions/top mirroring `snapshot-once.test.ts`.

## 7. Milestones

| # | Deliverable | Definition of done |
|---|---|---|
| M0 | Housekeeping | PID-reuse-guard work committed; `core/kill.ts` extracted; all tests green |
| M1 | `sessions` view | List/sort/filter/kill/snapshot; usable standalone as `pgops sessions` |
| M2 | Cockpit | `pgops` bare = live triage screen; drill + Esc navigation; health cards; degradation behavior |
| M3 | Snapshot parity | `--snapshot` on home/sessions/top; **v0.1 feature-complete** |
| M4 | Ship | version 0.1.0 on npm (`npx pgops` works cold); GitHub Actions CI (typecheck + tests, Node 20/22); README rewritten around the cockpit with demo GIF; CONTRIBUTING + issue template; repo public; launch posts (r/PostgreSQL, Hacker News "Show HN", lobste.rs) |

M1–M3 are this session's build target ("feature-complete first"). M4 is the
immediate follow-on and should not wait for any further features.

## 8. Out of scope for v0.1 (explicit)

- Full `vacuum`, `slots`, `parts`, `review`, `explain`, `events` views — the
  health cards are their only v0.1 presence.
- MCP server — **strongest v0.2 candidate**: the pure `render.ts`/snapshot layer
  means an MCP server is a thin wrapper exposing `triage`, `locks`, `sessions`,
  `top` as tools. Nobody owns "Postgres incident context for agents" yet.
- Config files, saved connections, multi-database switching.
- Windows terminal certification (Ink generally works; not a v0.1 gate).

## 9. Success criteria

- A dev who has never read the docs runs `npx pgops` against a misbehaving
  database and identifies the problem class in under a minute.
- An idle-in-transaction incident is resolvable entirely inside pgops:
  spot on cockpit → Enter → kill → verdict clears on next poll.
- `pgops --snapshot` output pasted into Slack is self-explanatory.
- All existing behavior (`pgops locks`, `pgops top`, flags) unchanged.
