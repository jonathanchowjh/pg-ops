# P5 · The Remaining Actions Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

## Why two of the six are declined

The parity spec's §7 states "all of the hard *lite* calls are in P6." **That is wrong, and this plan corrects it.** #19 `enable_query_stats` is `CREATE EXTENSION pg_stat_statements` and #61 `disable_query_stats` is the matching removal — DDL against a **monitored** database. Four independent commitments in this repository forbid that, and they were made at four different times by three different specs:

| Forbids it | Where |
|---|---|
| The README promise | *"pgops runs no DDL against a monitored database. Given `PGOPS_STORE_URL` it creates and migrates its own `pgops` schema in that store, **and nowhere else**."* — parity spec §3.3 |
| A mechanical guard | `apps/web/test/guards.test.ts` → `the DDL boundary`, whose regex matches the extension statements across **both** `packages/checks/src` and `apps/web`, and which pins its allowlist by exact equality |
| The action ladder | tier 3 = DDL = *"CLI only. Never reachable from the web."* — web spec §7.1 |
| §8 `Cut` | `packages/cli` was cut outright, and `pgops init` reduced to boot-only. **There is no tier-3 vehicle left** to put them in |

And a fifth reason specific to #61: removing the extension irreversibly destroys every query statistic on a production database, and pgops's own capture scheduler reads that extension every five minutes. A console with a control that deletes the data its own history feature collects is not a sharp edge, it is incoherent.

**The remedy path already exists and is better.** `run.ts`'s `remedyFor` turns a missing extension into the exact statement an operator should run themselves, and `queryStats` already declares `requires`. An operator who lands on `/queries` without the extension is told what to run. That is the correct division: pgops diagnoses, the operator's own migration tooling executes.

**Consequence for the trajectory.** The parity spec §7 ends *"43 planned → 0 planned, 2 declined."* It becomes **4 declined**. #59 `system_stats` is the third (already decided in §7, still carrying `planned: 'P6'` in the registry — **that one-line fix belongs to P6, not here**).

## Why the bulk kill is N guarded kills

pgHero's is `running_queries(...).each { |q| kill(q[:pid]) }` — an unguarded sweep, and its `kill` is a bare `pg_terminate_backend(pid)`. pgops's is not, and #13 `kill_all` is already **permanently declined** for being "an action with no diagnosis."

The property that makes #12 legitimate where #13 is not is the **diagnosis**: a duration filter over `pg_stat_activity` naming which sessions, shown to the operator before anything happens. So this ships as the existing `killBackend` applied N times — each target pinned to its own `backend_start` captured at render, each refused independently if its pid was recycled, each separately audited. Nothing about the single-kill guard is loosened or bypassed. The return is **per-session outcomes**, never a boolean: an operator told "done" when three of five were refused would believe sessions are gone that never were.

## Global Constraints

- `packages/checks` stays framework-free; its `dependencies` are exactly `["pg"]`.
- **`ACTIONS` is the only way to reach an action.** `packages/checks/src/index.ts` re-exports action modules' **types only**; the functions are reachable through `ACTIONS` alone. `guards.test.ts` enforces which files may name it — **that guard's file list widens in this phase and must be updated deliberately, never by deletion.**
- **Every action audits, success or failure**, through `writeAudit`, from a `finally` block, with the subject fields (`pid`, `database`, …) spread **after** caller-supplied `extra` so metadata cannot overwrite them. `kill.ts` is the reference implementation; copy its shape including the inner try/catch around the audit write.
- **The tier gate is checked in two places and neither is redundant.** `proxy.ts`'s `ACTION_PATH` regex gates the path above method dispatch (this is what makes a flagless deployment indistinguishable from a build without the file); each route re-checks `actionsAllowed`. **Both must learn the new paths.**
- **404, never 403**, when actions are off. A 403 advertises an endpoint that is merely switched off.
- **`application/json` required** on every action route, below the tier gate and above everything else. This is the CSRF defence: a cross-origin form can send a body that parses as JSON but cannot set this header.
- **Null discipline.** `null` means "we could not look". `??`, never `||`.
- **No `<Refresh>` added anywhere.** The three pages gaining controls already have the poll status they should have; `guards.test.ts` fails in both directions.
- **The DDL boundary regex strips comments but NOT string literals.** A `declined:` reason that spells the extension statements inside a string literal trips the guard. Word around it — see Task 5's trap, which is the single most likely way to lose an hour in this phase.
- Two typechecks, both must pass: `npm run typecheck:test` and `npm run --workspace @pgops/web typecheck` (resolves `@pgops/checks` through built `dist/` — rebuild before believing it).
- **Never run two of `test:web` / `test:int` / the web typecheck concurrently**, and **after any interrupted run, `kill` whatever still listens on 3100/3101** before re-running. An orphaned `next-server` silently answers the next run's requests and fakes a failure.

## Verified facts this plan depends on

Each was checked against a live server, not inferred. Re-verify if you doubt one; do not quietly change the code to match a guess.

1. **`pg_stat_statements_reset` takes three arguments portably.**
   - PG 14: `(userid oid DEFAULT 0, dbid oid DEFAULT 0, queryid bigint DEFAULT 0) -> void`
   - PG 17: `(userid, dbid, queryid, minmax_only boolean DEFAULT false) -> timestamp with time zone`

   **Passing a fourth argument breaks PG 14**, which is in the CI matrix. Pass exactly three. **Do not rely on the return value** — it is `void` on 14 and a timestamp on 15+; pgHero's "unknown OID 2278" comment is about that `void` and predates the change.
2. **`pg_stat_reset()` returns `void`** on every supported version.
3. **Scoping by `dbid` is a safety property, not decoration.** `pg_stat_statements` is shared across every database in the cluster. `pg_stat_statements_reset(0, <oid of current_database()>, 0)` resets only this database's statements; the zero-argument form wipes the cluster's. pgHero scopes it and so must this.
4. **Identifier quoting is done by the catalog, because no caller ever supplies a table name.** `quote_ident(n.nspname) || '.' || quote_ident(c.relname)` returns `"we;ird"."tab""le"` for a schema named `we;ird` holding a table named `tab"le`, and `ANALYZE` on that string succeeds. The list of tables comes from `pg_class`, so there is no user string in the statement at all — this is stronger than escaping one.
5. **`ANALYZE` is not matched by the DDL guard's regex** (which covers `CREATE`/`ALTER`/`DROP` + object, `TRUNCATE`, `GRANT`). It is still a write against a monitored database, which is why it is tier 1 and gated.
6. **`longRunning` does not return `backend_start`; `sessions` does**, as `backend_start::text AS backend_start` mapped to `backendStart: string | null`. Task 1 closes that gap, mirroring `sessions` exactly.

### Task 1: `backendStart` on `longRunning` — the identity the bulk kill is pinned to

**Files:**
- Modify: `packages/checks/src/checks/long-running.ts`
- Test: `packages/checks/test/long-running.test.ts`, `packages/checks/test/long-running.int.test.ts`

**Interfaces:**
- Consumes: `Check<LongRunningRow, LongRunningData, LongRunningOpts>`; `sessions.ts`'s existing `backend_start::text AS backend_start` → `backendStart: string | null` mapping, which this mirrors **field name for field name**.
- Produces: `LongRunningRow` gains `backend_start: string | null`; `LongRunning` gains `backendStart: string | null`.

**Why this is a task and not a line in Task 2.** `killBackend`'s whole PID-reuse guard is that the identity was captured **at selection time**, before the human delay, and compared inside the same statement as the terminate. A bulk kill whose targets carry no identity is a bulk kill with no guard — it would have to re-derive `backend_start` server-side, which compares the server's current idea of the session against itself and always agrees. So the identity has to reach the client, which means it has to come out of the check, which means the check changes first and independently.

**Traps:**
- **`::text`, not the raw timestamptz.** `sessions.ts` casts because the value round-trips through JSON to the browser and back into `$2::timestamptz`. A `Date` would be re-serialised by JSON with millisecond truncation and stop matching. Copy the cast.
- **Nullable.** `pg_stat_activity.backend_start` is null for some backend types. The type is `string | null` and `killBackend` already accepts null (meaning "kill on pid alone").
- **The `::text`-alias `ORDER BY` guard** in `boundaries.test.ts` bounds each `ORDER BY` at its own `LIMIT` or closing paren. This SQL's `ORDER BY query_start ASC, pid` sorts on neither alias; leave it alone.
- **`total_matching` must keep working.** It is `count(*) OVER ()::int` and is how `map` sets `truncated` without seeing `Opts`. Adding a column does not disturb it — but do not "tidy" it.

### Task 2: `killLongRunning` — #12 as N guarded kills

**Files:**
- Modify: `packages/checks/src/actions/kill.ts`
- Test: `packages/checks/test/kill.int.test.ts`

**Interfaces:**
- Consumes: `killBackend(ctx, target: KillTarget, meta: KillMeta): Promise<KillOutcome>`; `KillTarget = { pid: number; backendStart: string | null }`; `KillOutcome = 'terminated' | 'session-changed' | 'gone'`.
- Produces:
  ```typescript
  export interface BulkKillResult { pid: number; outcome: KillOutcome }
  export async function killLongRunning(
    ctx: CheckContext, targets: readonly KillTarget[], meta: KillMeta,
  ): Promise<BulkKillResult[]>
  ```

**Traps:**
- **Sequential, not `Promise.all`.** Each kill is a `pg_terminate_backend` on one pooled connection; firing N at once against a database already in trouble is the opposite of what an operator pressing this needs. It also makes the audit records interleave unpredictably. `for … of` with `await`.
- **One failure must not abandon the rest.** `killBackend` **rethrows** on a database error (its `finally` audits first, then the catch rethrows). A bulk kill that stops at the first permission error leaves the operator with no idea which of the remaining sessions were touched. Catch per target and record the failure as that target's outcome.
- **`KillOutcome` cannot express "errored".** Widening it would change the single-kill route's contract. Keep the union and add a **fourth member on `BulkKillResult` only**, as a separate optional `error?: string` field — or widen deliberately and update the single route. **Decide in this task and write the reasoning down.** The plan's recommendation: add `error?: string` to `BulkKillResult`, leaving `KillOutcome` untouched, because the single-kill route already surfaces an error as a 502 with a JSON body and does not need a new outcome.
- **No new audit record for the batch.** N kills write N records, which is *more* auditable than one summary. Do not add a summarising write — it would be a record of an event that is not a single event.
- **An empty target list is not an error.** It is a no-op returning `[]`. The route rejects an empty list before calling, because an operator who pressed a button expects something to have happened; the action itself stays total.

```typescript
export interface BulkKillResult {
  pid: number;
  outcome: KillOutcome;
  /**
   * Present only when `killBackend` threw — typically the console's role
   * lacking `pg_signal_backend`.
   *
   * A field rather than a fourth `KillOutcome`: widening that union would
   * change the single-kill route's contract, which already surfaces a throw
   * as a 502 carrying the message and has no use for a new outcome. The
   * outcome stays `gone` in that case because nothing was observed to die —
   * and the error field is what stops that reading as "it was already
   * finished".
   */
  error?: string;
}

/**
 * #12, and the reason it is not #13.
 *
 * pgHero's `kill_long_running_queries` is `running_queries.each { kill(pid) }`
 * over a bare `pg_terminate_backend`. `kill_all` is declined here permanently
 * as "an action with no diagnosis"; what makes THIS one legitimate is that the
 * targets were named by a duration filter and shown to the operator before
 * anything happened.
 *
 * So it is not a sweep. It is `killBackend` applied N times, and every
 * property of the single kill survives intact: each target is pinned to the
 * `backend_start` captured when the operator was looking at it, each is
 * refused independently if its pid was recycled onto another session, and each
 * writes its own audit record. N records, not one summary — a batch is not a
 * single event and recording it as one would lose which session was which.
 *
 * Sequential, deliberately. These are `pg_terminate_backend` calls against a
 * database already unwell enough for someone to be pressing this; firing them
 * concurrently is the opposite of what that operator needs, and it would
 * interleave the audit trail for no gain.
 *
 * One target failing does not abandon the rest. `killBackend` rethrows on a
 * database error (after auditing it), and a bulk kill that stopped at the
 * first permission error would leave the operator unable to say which of the
 * remaining sessions had been touched.
 */
export async function killLongRunning(
  ctx: CheckContext,
  targets: readonly KillTarget[],
  meta: KillMeta,
): Promise<BulkKillResult[]> {
  const results: BulkKillResult[] = [];
  for (const target of targets) {
    try {
      results.push({ pid: target.pid, outcome: await killBackend(ctx, target, meta) });
    } catch (err) {
      results.push({
        pid: target.pid,
        outcome: 'gone',
        error: err instanceof Error ? err.message : String(err),
      });
    }
  }
  return results;
}
```

### Task 3: `resetQueryStats` and `resetStats` — #20 and #31

**Files:**
- Create: `packages/checks/src/actions/stats.ts`
- Test: `packages/checks/test/stats-actions.int.test.ts` (create)

**Interfaces:**
- Consumes: `CheckContext` (`ctx.target` is the `Pool` for the monitored database); `writeAudit` from `./audit.js`.
- Produces:
  ```typescript
  export async function resetQueryStats(ctx: CheckContext, meta: ActionMeta): Promise<void>
  export async function resetStats(ctx: CheckContext, meta: ActionMeta): Promise<void>
  ```

**Interfaces:**
- Consumes: `CheckContext`; `ActionMeta` (from `types.ts`, see Task 3); `visibleSchemas(col: string): string` from `checks/indexes.ts`.
- Produces:

**What pgHero does.** `analyze_tables(verbose:, min_size:, tables:)` takes `table_stats`, rejects `information_schema` and `pg_catalog`, optionally filters on `size_bytes > min_size`, then for each runs `ANALYZE <quoted>` inside a transaction with `lock_timeout: 5000` and `statement_timeout: 120000`, rescuing a failure, printing it to stderr and recording `success: false` on that row. **Copy all of it except the stderr print**, which becomes the returned `error` string.

**The injection question, answered by removing the surface rather than escaping it.** `ANALYZE` cannot take a parameterised identifier, so the table name has to be interpolated. pgHero escapes a caller-supplied name with `quote_table_name`. This does something stronger: **no caller ever supplies a name.** The relation list comes from `pg_class`, and the catalog query itself returns the already-quoted, schema-qualified identifier:

```sql
quote_ident(n.nspname) || '.' || quote_ident(c.relname) AS qualified
```

Verified against a schema literally named `we;ird` holding a table named `tab"le`: it returns `"we;ird"."tab""le"` and `ANALYZE` on that string succeeds. There is no user string in the statement at all, which is a property an escaping function cannot give you.

**Traps:**
- **`SET LOCAL`, inside the transaction.** A bare `SET statement_timeout` on a pooled connection leaks to whatever uses that connection next — and this pool is shared with every check on the page. `BEGIN; SET LOCAL lock_timeout = '5s'; SET LOCAL statement_timeout = '120s'; ANALYZE …; COMMIT;` on a **checked-out client**, not on the pool.
- **One client, checked out once, released in a `finally`.** `run.ts`'s `guardClient` exists for exactly this: it swallows the connection-error event and returns a release function. Use it — a client that errors mid-ANALYZE and is released without it emits an unhandled `error` event.
- **A failure rolls back its own transaction and the loop continues.** After a caught failure the client is in a failed transaction and **every subsequent statement on it errors until ROLLBACK**. Issue the `ROLLBACK` in the catch, or check out a fresh client per table. The plan's recommendation: one client for the batch, `ROLLBACK` in the catch — checking out N clients from a pool sized for a web console is how a bulk action becomes an outage.
- **The cap is not optional.** A database with 40,000 relations would otherwise issue 40,000 `ANALYZE`s from a request handler. Default `limit` to something small (50) and have the route pass it; state the cap in the result the surface renders.
- **`ANALYZE` is a write, and the DDL guard does not catch it.** That is correct — the guard covers `CREATE`/`ALTER`/`DROP`/`TRUNCATE`/`GRANT` — but do not read its silence as permission to add other writes here.

```typescript
// packages/checks/src/actions/analyze.ts
import type { CheckContext } from '../types.js';
import { guardClient } from '../run.js';
import { visibleSchemas } from '../checks/indexes.js';
import { writeAudit } from './audit.js';
import type { ActionMeta } from '../types.js';

export interface AnalyzeResult {
  /** Schema-qualified and already quoted, exactly as issued. */
  relation: string;
  ok: boolean;
  error?: string;
}

export interface AnalyzeOpts {
  /** Skip tables smaller than this. pgHero's `min_size`. */
  minSizeBytes?: number;
  /** Hard cap on how many statements one press may issue. */
  limit?: number;
  /** Per-table lock wait. pgHero uses 5s; lowered only by tests. */
  lockTimeoutMs?: number;
  /** Per-table statement ceiling. pgHero uses 120s. */
  statementTimeoutMs?: number;
}

/**
 * The relation list, with the catalog doing the quoting.
 *
 * `ANALYZE` cannot take a parameterised identifier, so the name is
 * interpolated — and the defence is not an escaping function but the absence
 * of a caller-supplied name in the first place. Every identifier here comes
 * out of pg_class already quoted by `quote_ident`, verified against a schema
 * named `we;ird` holding a table named `tab"le`.
 *
 * Ordered largest first: if the cap clips the list, the tables whose
 * statistics matter most are the ones that got analyzed.
 */
const TABLES_SQL = `
SELECT quote_ident(n.nspname) || '.' || quote_ident(c.relname) AS qualified
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE c.relkind = 'r'
  AND ${visibleSchemas('n.nspname')}
  AND pg_total_relation_size(c.oid) >= $1
ORDER BY pg_total_relation_size(c.oid) DESC, n.nspname, c.relname
LIMIT $2`;

/**
 * #47. One ANALYZE per table, each in its own transaction with its own
 * timeouts, each failure recorded rather than thrown.
 *
 * `SET LOCAL`, never a bare `SET`: this client comes from the pool every check
 * on the page shares, and a statement_timeout left behind would apply to
 * whatever ran next on it. `SET LOCAL` is scoped to the transaction and
 * unwinds with it.
 *
 * One client for the batch, with a ROLLBACK in the catch. After a failed
 * statement the connection is in a failed transaction and every subsequent
 * statement on it errors until it is unwound — so the rollback is what lets
 * the loop continue at all, not tidiness. Checking out a fresh client per
 * table instead would drain a pool sized for a web console.
 */
export async function analyzeTables(
  ctx: CheckContext,
  meta: ActionMeta,
  opts: AnalyzeOpts = {},
): Promise<AnalyzeResult[]> {
  const lockMs = opts.lockTimeoutMs ?? 5_000;
  const stmtMs = opts.statementTimeoutMs ?? 120_000;
  const results: AnalyzeResult[] = [];
  let result = 'unknown';

  try {
    const { rows } = await ctx.target.query<{ qualified: string }>(
      TABLES_SQL, [opts.minSizeBytes ?? 0, opts.limit ?? 50]);

    const client = await ctx.target.connect();
    const release = guardClient(client);
    try {
      for (const { qualified } of rows) {
        try {
          await client.query('BEGIN');
          await client.query(`SET LOCAL lock_timeout = ${lockMs}`);
          await client.query(`SET LOCAL statement_timeout = ${stmtMs}`);
          await client.query(`ANALYZE ${qualified}`);
          await client.query('COMMIT');
          results.push({ relation: qualified, ok: true });
        } catch (err) {
          // Unwind before the next iteration: until this runs, every statement
          // on this connection fails with "current transaction is aborted".
          await client.query('ROLLBACK').catch(() => {});
          results.push({
            relation: qualified,
            ok: false,
            error: err instanceof Error ? err.message : String(err),
          });
        }
      }
    } finally {
      release();
    }

    const failed = results.filter((r) => !r.ok).length;
    result = failed === 0 ? `ok: ${results.length}` : `partial: ${results.length - failed} ok, ${failed} failed`;
    return results;
  } catch (err) {
    result = `error: ${err instanceof Error ? err.message : String(err)}`;
    throw err;
  } finally {
    try {
      await writeAudit({
        action: 'analyze',
        subcommand: meta.subcommand,
        ...(meta.actor ? { user: meta.actor } : {}),
        target: { ...meta.extra, relations: results.map((r) => r.relation) },
        reason: meta.reason,
        result,
      });
    } catch (err) {
      console.error('pgops: writeAudit threw despite its no-reject contract; analyze unaffected:', err);
    }
  }
}
```

**`SET LOCAL lock_timeout = ${lockMs}`** interpolates a number the caller may supply. That is the one interpolation in this file that is not catalog-sourced. **Guard it**: coerce with `Math.max(0, Math.trunc(Number(...)))` before use, or reject a non-finite value. Decide and write it down — an options object reached from a route is caller-controlled.

### Task 6: `lib/action-route.ts` — the shared preamble and typed confirmation

**Files:**
- Create: `apps/web/lib/action-route.ts`
- Test: `apps/web/test/action-route.test.ts` (create)

**Interfaces:**
- Consumes: `actionsAllowed(env)`; `ACTOR_HEADER`; `contextFor(name)` / `UnknownDatabaseError` from `@/lib/pools`.
- Produces:
  ```typescript
  export interface ActionRequest {
    ctx: CheckContext;
    /** `<user>@<host>`, never left to currentActor(). */
    actor: string;
    reason: string;
    body: Record<string, unknown>;
  }
  /** Either the parsed request, or the Response to return instead. */
  export async function openAction(
    req: Request, name: string, opts?: { confirm?: string },
  ): Promise<ActionRequest | Response>
  ```

**Why a helper and not five copies.** The kill route's preamble is ~60 lines of gate, media type, body parse, reason validation, context resolution and actor derivation, and **every line of it is load-bearing security**. Five hand-maintained copies is five places for one of them to drift, and the drift would be silent. This is precisely the case the house style names: several functions passing the same values around. It stays a **bare function**, not a class — there is no shared state between calls.

**Traps:**
- **Order is not stylistic.** Tier gate (404) → media type (415) → body → reason → confirmation → context. A 415 above the tier gate advertises a route that is switched off; the kill route's comments say this explicitly and the same reasoning applies to all five.
- **Returning `Response | ActionRequest`** means every caller must narrow. `if (opened instanceof Response) return opened;` — write it in every route and do not "simplify" it into a thrown error, which would need a catch in each route anyway and would make the 404 path an exception.
- **Typed confirmation is checked SERVER-SIDE or it is theatre.** A client-only confirmation is one `curl` away from bypassed. When `opts.confirm` is given, the body must carry `confirm` equal to it (the database name), compared exactly.
- **Do not fold `warnIfActionsAreUnauthenticated` in silently.** It latches on a module-level `warned`; moving it here makes one warning cover all five routes, which is *better* — but it changes observable behaviour and belongs in the commit message.
- **`contextFor` failures split two ways**: `UnknownDatabaseError` → 404 (nothing here to act on), anything else → 502 with a JSON body. Copy the kill route's split exactly.
